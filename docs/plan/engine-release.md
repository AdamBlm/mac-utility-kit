# Managed Video Tools release procedure

The DMG and engine feed have independent versions and signing keys. Local builds without feed configuration retain the executable pickers. A managed install writes four raw executables to a versioned per-user directory. Releases use raw assets so the app can verify their exact lengths and SHA-256 hashes without unpacking an archive.

## Prepare a release candidate

1. Use the official standalone [yt-dlp macOS executable](https://github.com/yt-dlp/yt-dlp/releases) and [Deno macOS releases](https://github.com/denoland/deno/releases). Run `scripts/fetch-release-video-inputs.sh <architecture> <yt-dlp tag> <Deno tag> <new output directory>`. The script checks yt-dlp’s pinned signing-key fingerprint and signed hashes, checks Deno’s published hash, and stages only the expected macOS executables. The official standalone yt-dlp includes EJS. The upstream project identifies its PyInstaller build as GPLv3+ because it includes GPL code. Include the exact bundled components, notices, and corresponding source in the redistribution review. Deno's project license is MIT. Include the notices for the exact bundled Deno runtime and dependencies. [yt-dlp binary licenses](https://github.com/yt-dlp/yt-dlp#licensing) · [Deno license](https://github.com/denoland/deno/blob/main/LICENSE.md)
2. Qualify a pinned native FFmpeg/FFprobe GPL build. Run `scripts/build-release-ffmpeg.sh` or dispatch the **Qualify FFmpeg release candidates** workflow. The build uses the pinned [Microsoft vcpkg FFmpeg port](https://github.com/microsoft/vcpkg/tree/74f5ea45ca78988784b810ad9bbb148ea7ff76d8/ports/ffmpeg) with its static macOS triplets and an explicit GPL feature set. The workflow retains build inputs and runs the existing tests against the resulting pair. Check libx264, libx265, libvpx, libopus, libvorbis, libmp3lame, libass, PNG decoding, lavfi fixtures, and VideoToolbox. Check the precise dependency versions, build configuration, and every license, and reject a build containing `--enable-nonfree`. Publish corresponding source, license notices, build instructions, and patches for each distributed version. Rely on the exact reviewed binaries for release fixtures. [FFmpeg licensing](https://ffmpeg.org/doxygen/trunk/md_LICENSE.html)
3. Verify artifacts with Gatekeeper on a clean Mac, including browser download of the app. Where upstream artifacts need release signing/notarization, sign and notarize the exact artifacts using the release identity and verify before capturing hashes. Preserve the notices for the upstream and bundled components. Exercise a real authorized URL download with split streams, encoding and subtitles, offline behavior where supported, and the core media regression fixtures.
4. Stage the final binaries as `artifacts/<arm64 or x86_64>/<yt-dlp, deno, ffmpeg, ffprobe>`. Prepare a reviewed JSON file with a positive ascending `revision` and `platforms` keyed by architecture. Each architecture maps executable names to records with `version`, `minimumMacOS` (major version, at least 15), `sha256` (after signing), `url` (immutable binary URL), and `notices`. FFmpeg, FFprobe, and the standalone yt-dlp also require a `source` URL. The preparation script verifies the local binary hash, signature, architecture, library links, FFmpeg flags, and advertised capabilities.
5. Run the release commands below. Upload immutable binaries, sources, and notices before switching the HTTPS feed to the new signed manifest. The scheduled upstream check reports new release candidates for review. Keep the signing key in the release environment, and retain older source and notices for the binaries already distributed.

```sh
python3 scripts/prepare-video-engine-manifest.py reviewed.json artifacts manifest-payload.json
swift scripts/sign-engine-manifest.swift manifest-payload.json video-engines.json
```

The manifest signer reads `MUK_VIDEO_ENGINE_SIGNING_KEY` from the release environment. Use `swift scripts/sign-engine-manifest.swift --generate-key` in a private release environment to generate a dedicated engine key pair.

## Package the app

Set `MUK_VIDEO_ENGINE_FEED` and `MUK_VIDEO_ENGINE_PUBLIC_KEY` to configure the managed installer. Set `MUK_APPCAST_URL` and `MUK_APPCAST_PUBLIC_KEY` for Sparkle. Use Sparkle's official `generate_keys` and `generate_appcast` tools and keep the app update key separate from the engine signing key. Package with `scripts/build-app.sh` and `scripts/build-dmg.sh` using the Developer ID identity and notary profile. Host the notarized DMG and the signed Sparkle update archive through the release hosting. [Sparkle publishing guide](https://sparkle-project.org/documentation/publishing/)

Gate stable release on a private preview, then public beta. On each supported clean Mac and architecture, verify first-use setup with no existing engines, explicit cancellation, failed signature and failed hash recovery, successful update, rollback, and preserved explicit executable selection. For Sparkle, use two real Developer ID builds to verify a signed update through the promoted appcast.
